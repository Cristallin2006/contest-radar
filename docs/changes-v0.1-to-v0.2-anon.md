# 竞赛赛程系统 v0.2-anon 变更说明

- 日期：2026-11-23
- 原设计：v0.1《竞赛情报与个人赛程系统》需求文档 + 架构设计
- 新设计：v0.2-anon《竞赛情报与公共赛历系统》需求文档 + 架构设计
- 结论：保留 v0.1 原文，不覆盖；v0.2 是匿名化删减版。

---

## 1. 一句话

从“有账号、有队伍、有履历的个人赛程系统”，收缩为“**公开竞赛情报 + 公共赛历 + 浏览器本地个人化 + 单管理员审核**”。

---

## 2. 删掉了什么

| 原模块 | 处理 | 原因 |
|---|---|---|
| ACC 账号/邀请码/角色/密码/TOTP | 全部删除 | 纯匿名访问，不做用户体系 |
| TEAM 队伍/组队/找队友/队友可见性 | 全部删除 | 没有身份，无法可靠表达“谁报了什么” |
| REC 服务端履历/证书/附件 | 全部删除 | 不做上传和私密数据；履历可放本地或现有 Seafile/Gitea |
| SCH 服务端关注/参赛状态/个人时间线 | 删除服务端部分 | 用 localStorage + ICS 替代，不跨设备 |
| SCH 邮件提醒/去重/发送 worker | v1 删除 | 用 ICS VALARM + 手机日历；邮件订阅列为 P2 |
| 用户级 iCal token | 删除 | 公共/地区 ICS + 前端导出收藏 ICS |
| 文件存储/附件/对象存储 | 删除 | 不存证书/附件 |
| 用户管理/邀请码/审计中的用户操作 | 删除 | 只保留管理员令牌和管理审计 |
| FastAPI/Postgres/独立 worker/Caddy/Redis | 不采用 | 匿名公开读 + 低频管理写，Node + SQLite + 现有 Nginx 足够 |

---

## 3. 保留了什么

| 原模块 | 保留情况 |
|---|---|
| EVT 赛事库 | 保留，并升级为系列 → 届次 → 阶段 |
| EVT 标签/筛选/搜索/详情 | 保留 |
| EVT 修改历史/来源/最后核实时间 | 保留 |
| EVT 采集同步/待审核 | 保留，管理员审核后发布 |
| PUB 公开访问 | 保留，默认国内，可切国外 |
| SCH 公共 ICS | 保留，按阶段生成 VEVENT + VALARM |
| 本地收藏/隐藏/我的赛程 | 新增，localStorage |
| 本地画像/匹配评分 | 新增，纯前端 |
| 管理员审核/数据源状态/备份 | 保留，单令牌模式 |
| 安全/备份/监控 | 保留，但按匿名场景简化 |

---

## 4. 新增了什么

1. **公开列表 + 详情 + 月历**，默认国内，地区/类别/方向/赛制/状态/时间筛选。
2. **系列/届次/阶段**三层数据模型，支持一场比赛多个阶段。
3. **本地个人化**：收藏、隐藏、我的赛程、本地画像、匹配评分、导出/导入 JSON。
4. **收藏 ICS 导出**：浏览器生成，不上传收藏列表。
5. **单管理员令牌 + 待审核区 + 修改历史 + 审计**。
6. **公开变更页**（P1）：新增/时间变更/取消。
7. **匿名线索提交**列为 P2，且必须加验证码/限流，避免垃圾。

---

## 5. 为什么这样改

1. **原设计的核心价值在账号/队伍/履历**；删掉这些后，继续用 FastAPI/Postgres/worker 是过度设计。
2. **当前已有可运行的 Node + SQLite 竞赛雷达**，复用采集器/分类/赛历，改造成本最低。
3. **服务器压力**：匿名版新增内存约 50–150MB，当前 4C4G 共享服务器完全够；1C1G/2C2G 也能跑。
4. **维护成本**：一个人维护，组件越少越好；没有用户数据，没有密码/邮件/附件/备份合规压力。
5. **交付速度**：匿名 MVP 约 1–2 周；原完整 MVP 约 6–7 周。

---

## 6. 代价

- 没有跨设备个人赛程；换浏览器要导出/导入 JSON。
- 没有队伍协作/“谁报了什么”。
- 没有服务端履历/证书附件；只能本地或 Seafile/Gitea。
- v1 没有邮件提醒；只能 ICS + 手机日历。
- 公开站会被爬取；需要限流/缓存，管理入口要保护。
- 以后要加账号/队伍，仍需迁移；但 v0.1 架构可以复用。

---

## 7. 服务器影响

| 项目 | 匿名版 |
|---|---|
| 运行组件 | Node 应用 + 现有 Nginx + SQLite |
| 新增内存 | 约 50–150MB |
| 新增磁盘 | 数据库几十 MB + 备份；镜像约 100–200MB |
| Postgres/Redis/Caddy | 不需要 |
| 当前 4C4G | 完全够，甚至可以更小 |
| 独立服务器 | 不需要；以后加账号/队伍再评估 |

之前“4C4G 共享是否够”的顾虑，在匿名版下基本消失。

## 8. 迁移顺序（从当前原型）

1. 建 `event_series / event_editions / event_stages / tags / edition_changes / ingest_items / sources / admin_audit`。
2. 把当前 68 条 `competitions` 映射成届次 + 阶段；按别名合并系列。
3. 采集器改为写 `ingest_items`，管理员审核后发布。
4. 新增管理页（令牌 + 待审核 + CRUD + 数据源 + 审计）。
5. 新增本地收藏/画像/匹配/ICS 导出。
6. 公开 API `/api/v1/editions`，前端切换。
7. 旧表保留只读一个版本，确认后删除。

## 9. 对既有评审意见的吸收

匿名版删掉了账号/队伍/邮件/附件，评审中与这些相关的 S1（会话、CSRF、邮件去重、附件校验、越权）不再适用；但以下与匿名版仍相关的意见已经吸收：

- **时间语义**：阶段区分 `starts_at/ends_at`、`deadline_at`、`time_status`（已确认/暂定/待定）、`is_all_day`；只有截止点的阶段不再用“开始=结束”伪装；待定/暂定不生成精确提醒。
- **状态语义**：届次存生命周期（正常/延期/取消/结束），展示状态按阶段推导，允许多阶段状态并存；“归档”不等于“取消”。
- **报名语义**：拆成报名组织方式（个人/队长/学校）和提交渠道（网站/邮箱/其他），保留学校/队内截止说明。
- **iCal**：稳定 UID、SEQUENCE/LAST-MODIFIED；截止点只用 DTSTART；取消/延期保留 UID；说明客户端刷新/响铃差异，不承诺所有手机即时提醒。
- **CTFtime 合规**：CTFtime API 有用途限制，不假设可以做克隆；只存必要字段并链接原文，必要时联系对方确认。
- **SSRF**：DNS 解析后连接已验证 IP，保留 Host/TLS SNI，防 DNS rebinding；限制重定向和响应体大小。
- **多租户**：不在 v0.2 预留 `team_id` 半成品字段；未来多队按独立部署/重新设计隔离，而不是所有表加一列。
- **编辑后台**：如果以后重写，可考虑 Django Admin 省工；当前已有 Node 原型，优先复用。

## 10. 如果以后要恢复账号/队伍/履历

- 直接回到 v0.1 的模块划分和 Postgres 设计；
- v0.2 的公开赛事库/采集器/ICS/管理审核可以保留；
- 需要新增 `users / sessions / follows / teams / records / attachments`，并把 SQLite 迁到 Postgres；
- 不要只在所有表加一个 `team_id`；权限、唯一键、缓存、任务、文件、订阅都要重新设计，或独立部署。

---

## 11. 需要你确认的点

1. 站点是否完全公开可搜索，还是只发链接？
2. 管理入口是否加 IP 白名单/VPN，还是公网强令牌即可？
3. 是否接受“没有邮件提醒，只靠 ICS”？
4. 是否需要匿名线索提交（会有垃圾风险）？
5. 以后是否可能恢复账号/队伍/履历？如果可能，按 v0.1 重新设计，不在 v0.2 预留半成品字段。
